# Card API

`card-api` обслуживает карточки происшествий и учебный процесс для ролей
`STUDENT` и `TEACHER`. Базовый префикс REST API — `/api/v1`, проверка сервиса —
`GET /health`.

Подробные frontend-контракты находятся рядом с кодом соответствующих вкладок.

## Общие методы

Обе роли используют общие справочники, карточки происшествий, списки назначений
и данные учебных сессий из пакета `common`. Конкретные общие методы перечислены
в README тех вкладок, где они нужны frontend.

## Переключение авторизации

При `AUTH_ENABLED=false` (в контейнерах — `S112_AUTH_ENABLED=false`) действует
прежний контракт: клиент передаёт `X-User-Id` или ID действующего пользователя
в query/теле метода. При `AUTH_ENABLED=true` все методы card-api, кроме `/health`,
требуют `Authorization: Bearer <access_token>` и определяют действующего
пользователя по `sub` проверенного JWT. `X-User-Id` и поля действующего лица
(`actor_id`, `teacher_id`, `created_by`, `updated_by`, `deleted_by`,
`assigned_by`, `user_id`, `operator_id`, `author_id`) можно не передавать;
если они переданы, сервер использует ID из токена. Тело может отсутствовать
при вызовах готовности и запуска назначения, завершения сессии, действий со
звонком без дополнительных полей, индивидуального abort и ручного выпуска.
ID целевого обучаемого, участника или группы
по-прежнему передаётся в параметре соответствующего метода.

При включённой авторизации сервер также проверяет роль и доступ к конкретной
сессии, группе, workspace и карточке. `401` означает отсутствие или
недействительность токена, `403` — недостаточные права. Для SSE `/events`
нужен тот же Bearer-токен и членство в указанном workspace.

Полная машинная схема доступна в OpenAPI запущенного сервиса: `/docs` и
`/openapi.json`.

Полный контракт SSE, включая все типы событий, фильтры, дедупликацию и
восстановление после разрыва, описан в
[`../realtime_gateway/README.MD`](../realtime_gateway/README.MD).
