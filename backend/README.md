# Backend учебного симулятора Системы-112

Текущий этап реализует карточки происшествий, учебные сценарии, изолированные
рабочие пространства и инфраструктуру надёжного распространения событий.

## Сервисы

- `card-api` — FastAPI REST API, записывает карточку, историю, read-модель и
  outbox-событие одной транзакцией PostgreSQL.
- `outbox-worker` — публикует события из `outbox_event` в Kafka с семантикой
  at-least-once и сохранением порядка версий одной карточки. PostgreSQL
  `LISTEN/NOTIFY` пробуждает воркер после commit; опрос раз в 50 мс страхует
  от пропущенных уведомлений.
- `speech-api` — отдельный GPU-сервис с GigaAM STT и Qwen3-TTS; поддерживает
  внутренние HTTP-методы `/api/v1/stt` и `/api/v1/tts`.
- `speech-request-worker` — читает STT/TTS-команды из Kafka, получает и
  сохраняет аудио через SeaweedFS и фиксирует результат вместе с result-outbox.
- `speech-result-worker` — идемпотентно переносит STT-текст в
  `training_action` и выпускает realtime-события.
- `dialogue-worker` — читает распознанные реплики звонка, получает потоковый
  ответ LLM и записывает ранние фразы как TTS-сегменты с outbox-заданиями.
- `semantic-evaluation-request-worker` — получает через Kafka ожидаемый и
  распознанный текст исходящего звонка и вызывает OpenAI-совместимый
  llama-server.
- `semantic-evaluation-result-worker` — идемпотентно записывает результат
  сравнения в `training_action`, realtime и состояние готовности сессии.
- `audio-reconciler` — удаляет оставшиеся после аварий объекты SeaweedFS, для
  которых не существует `audio_message` или `tts_segment`.
- `scenario-worker` — выпускает карточки сценария по временным и событийным
  триггерам, обновляет готовность завершения и автоматически завершает сессии
  с политикой `AUTO_WHEN_READY`; несколько экземпляров безопасно делят работу
  через блокировки БД.
- `realtime-gateway` — читает Kafka и передаёт события браузерам через SSE.
  При включённой аутентификации требует токен и членство в workspace.
- `admin-api` — FastAPI для административных вкладок; управляет локальными
  учётными записями, ведёт аудит и агрегирует PostgreSQL, Prometheus и Loki.
- `auth-api` — локальный вход по учётным записям `user_account` и выпуск общих
  JWT access token для `card-api` и `admin-api`.
- `postgres-primary` — основной узел PostgreSQL.
- `postgres-replica` — физическая streaming-replica; REST GET-запросы читают с неё.
- `kafka-1..3` — трёхузловой KRaft-кластер Kafka 3.4 на образе
  `bitnamilegacy/kafka:3.4`.
- `kafka-init` — создаёт realtime, audio и semantic-evaluation topics с шестью
  партициями, `replication.factor=3` и `min.insync.replicas=2`.
- `seaweed-master-1..3`, `seaweed-volume-1..2` и `seaweed-filer-1..2` —
  отказоустойчивое хранение аудио с копией данных в другом rack; filer metadata
  хранится в PostgreSQL.
- `prometheus` и `grafana` — хранение и визуализация метрик.
- `node-exporter`, `cadvisor`, два `postgres-exporter`, `kafka-exporter` и
  `blackbox-exporter` — метрики хоста, контейнеров, PostgreSQL, Kafka и HTTP.
- `loki` и `alloy` — хранение и сбор stdout/stderr Docker-контейнеров.
- `nvidia-gpu-exporter` — метрики NVIDIA GPU через `nvidia-smi`; запускается
  только профилем `gpu`.

## Модель классификации

Оператор выбирает группу происшествия и иерархию из трёх типовых признаков.
При сохранении проверяется принадлежность каждого признака его родительскому
уровню. Таблица `feature_schema` удалена; дополнительные признаки пока
необязательны и не проверяются по отдельной JSON Schema. Справочник
`incident_type` сохранён до следующего этапа переработки классификатора.

`card_feature` также содержит:

- индексируемый признак первого порядка;
- зависимый признак второго порядка;
- зависимый признак третьего порядка;
- остальные признаки в `additional_features JSONB`;
- поле итогового типа происшествия (пока не вычисляется);
- номер ревизии и пользователя, изменившего признаки.

Каждое изменение признаков сохраняется полным снимком в
`card_feature_history`.

`service_routing_rule` связывает `event_kind` со службой и содержит
условие по дополнительным признакам, способ доставки и тип происшествия,
принятый во внешней системе службы. Совпавшие правила формируют список
оповещения автоматически. Если одной службе нужны несколько каналов доставки,
они фиксируются отдельно в `card_service_dispatch`, но в списке оповещения
служба остаётся одной записью `card_service`. Оператор может только добавить
дополнительную службу вручную; такая запись получает причину `MANUAL`.
Начальная миграция заполняет справочник получателей объединённым перечнем из
двух предоставленных Excel-файлов; конкретные правила маршрутизации должны
загружаться из строк выбранной редакции классификатора.

## Локальный запуск

1. Скопировать `.env.example` в `.env`, заменить пароли и при необходимости
   изменить публикуемые на хосте порты.
   Для `speech-api` каталог `SPEECH_MODELS_DIR` должен содержать
   `GigaAM-v3-e2e-rnnt/`, `Qwen3-TTS-12Hz-0.6B-Base-Q8_0.gguf` и
   `mmproj-Qwen3-TTS-12Hz-0.6B-Base-F16.gguf`; файл голоса задаётся через
   `TTS_REFERENCE_AUDIO_FILE`. По умолчанию это `backend/models/` и
   `backend/reference.wav`: пути `./models` и `./reference.wav` в `.env`
   разрешаются относительно каталога `compose.yaml`. Эти файлы не входят в
   репозиторий; модели необходимо разместить самостоятельно. Если путь
   отсутствует, Compose не создаёт вместо него пустой каталог.
   Контекст сборки — `backend/`; исходники C++-воркера находятся в
   `backend/tts-worker/`. Модели, файл голоса и `.env` исключены из контекста
   через `.dockerignore` и не копируются в образ; модели и голос подключаются
   при запуске контейнера как read-only bind mounts.
   C++-воркер собирает одноразовый сервис `speech-tts-build`. Готовые библиотеки
   хранятся в volume `speech-tts-runtime`, а промежуточный CMake-кэш — в
   `speech-tts-build-cache`. При повторном запуске сборка пропускается, если
   отпечаток исходников, версии CUDA и `CUDA_ARCHITECTURES` не изменился.
   Значение по умолчанию `CUDA_ARCHITECTURES=75-real` соответствует RTX 2060;
   для другой видеокарты его нужно изменить в `.env`.
   Внешний llama-server должен слушать не только loopback, а адрес, доступный
   Docker-контейнерам (например, запускаться с `--host 0.0.0.0 --port 4555`).
   Worker обращается к нему через
   `S112_SEMANTIC_EVALUATION_API_URL=http://host.docker.internal:4555`; hostname
   сопоставляется host gateway в `compose.yaml`.
2. Из папки `backend` проверить, какие значения Compose прочитал из `.env`:

   ```shell
   docker compose --env-file .env config --environment
   docker compose --env-file .env config --quiet
   ```

3. Создать или пересоздать контейнеры с проверенной конфигурацией:

   ```shell
   docker compose --env-file .env up -d --build --force-recreate
   ```

`INFRA_BIND_ADDRESS`, `APP_BIND_ADDRESS` и `ADMIN_BIND_ADDRESS` обязательны:
если `.env` не найден или имя переменной записано неверно, Compose завершится
ошибкой до создания контейнеров. Команда `docker compose restart` не применяет
изменения портов — для них требуется пересоздание контейнера.

После запуска с портами по умолчанию:

- REST API и OpenAPI: `http://localhost:8080/docs`;
- SSE: `http://localhost:8081/events`;
- PostgreSQL primary: `localhost:5432`;
- PostgreSQL replica: `localhost:5433`;
- Kafka: `localhost:29092`, `localhost:39092`, `localhost:49092`.
- Admin API и OpenAPI: `http://localhost:8082/docs`;
- Auth API и OpenAPI: `http://localhost:8084/docs`;
- Speech API и OpenAPI: `http://localhost:8083/docs`;
- SeaweedFS filer: `http://localhost:8888` и резервный `http://localhost:8889`;
- Prometheus: `http://localhost:9090`;
- Grafana: `http://localhost:3000`.

По умолчанию все опубликованные порты привязаны к `127.0.0.1`. Для доступа
с другого компьютера используйте SSH-туннель или reverse proxy с TLS и
аутентификацией. Менять `APP_BIND_ADDRESS` на `0.0.0.0` без этих мер нельзя.
`INFRA_BIND_ADDRESS` для PostgreSQL и Kafka рекомендуется всегда оставлять
локальным. Пароль Grafana из `.env.example` необходимо заменить.

На Linux-сервере с NVIDIA-драйвером, доступной командой `nvidia-smi` и NVIDIA
Container Toolkit GPU-мониторинг включается отдельно:

```shell
docker compose --profile gpu up --build
```

Без профиля `gpu` остальные компоненты запускаются штатно, а API возвращает
`gpu.available=false`. `node-exporter` и cAdvisor рассчитаны на Linux-хост.

Все порты, публикуемые через Compose, задаются централизованно в `.env`:
`POSTGRES_PRIMARY_PORT`, `POSTGRES_REPLICA_PORT`, `KAFKA_1_PORT`,
`KAFKA_2_PORT`, `KAFKA_3_PORT`, `CARD_API_PORT`, `REALTIME_GATEWAY_PORT`,
`ADMIN_API_PORT`, `AUTH_API_PORT`, `PROMETHEUS_PORT` и `GRAFANA_PORT`. Привязка управляется
`INFRA_BIND_ADDRESS`, `APP_BIND_ADDRESS` и `ADMIN_BIND_ADDRESS`; внутренние
порты контейнеров менять не требуется.

Внешний адрес Kafka задаётся через `KAFKA_ADVERTISED_HOST`. При локальной
привязке это `localhost`. Если Kafka действительно нужна удалённым клиентам,
значение должно быть доступным им DNS-именем сервера, но сначала необходимо
настроить TLS/SASL и сетевые ограничения.

Миграции штатно выполняет одноразовый сервис `migrate`. При ручном запуске
Alembic можно находиться как в корне проекта, так и в `backend`; перед запуском
нужно явно передать `S112_DATABASE_URL` для того сетевого контекста, из которого
выполняется команда. Адрес `postgres-primary:5432` работает только внутри
Compose-сети, а с хоста используется опубликованный порт primary.

Миграция `0001` создаёт консолидированную схему карточек, администрирования и
обучения. `0002` добавляет сроки обработки карточек и позиции участников,
`0003` — начальных учебных пользователей, `0004` очищает сценарные определения
от runtime-полей, `0005` добавляет группы и экспертную оценку, а `0006` —
политики и состояние готовности завершения сценария. Миграция `0007` добавляет
`audio_message` и consumer inbox для идемпотентного STT/TTS-конвейера, а `0008`
— шаблоны и runtime-состояние входящих учебных звонков. Миграция `0009`
добавляет состояние процедурного генератора и идентичность созданных им
карточек.
Миграция `0012` добавляет TTS-сегменты, состояние генерации реплик и триггер
`LISTEN/NOTIFY` для outbox.

## Учебные сценарии

- `card_template` хранит неизменяемые версии исходной карточки, ожидаемый
  результат и правила оценки. `expected_result` содержит только `final_state`
  и `required_actions`; запрещённые действия не используются.
- `incoming_call_template` по тем же правилам версионирования хранит
  `initial_call` и `expected_result`; сценарий версии 2 может объединять
  элементы `INCIDENT_CARD` и `INCOMING_CALL`.
- Сценарий версии 3 может иметь режим `PROCEDURAL` или `HYBRID`. При назначении
  подходящие шаблоны фиксируются в snapshot, а scenario-worker выпускает их без
  повторений по встроенному пресету сложности.
- `training_scenario.definition JSONB` хранит карточки и `trigger_type`:
  `TIME_OFFSET`, `AFTER_ACTION` или `MANUAL`.
- `training_scenario.completion_policy` определяет способ завершения:
  `STUDENT_CONFIRM` и `AUTO_WHEN_READY` для индивидуального сценария,
  `TEACHER_ONLY` для общего.
- Сценарий со статусом `DRAFT` можно редактировать через `PATCH`. Перевод в
  `PUBLISHED` выполняется тем же запросом после проверки преподавателем;
  опубликованный сценарий больше не редактируется. `DELETE` безопасно переводит
  сценарий в `ARCHIVED`, сохраняя историю назначений.
- `learning_group` и `learning_group_member` хранят учебные группы и их текущий
  состав. Назначение индивидуального сценария группе создаёт отдельное
  назначение каждому активному участнику; назначение общего сценария создаёт
  одну совместную сессию с запуском преподавателем.
- При назначении ссылки на шаблоны разрешаются в неизменяемый
  `scenario_assignment.scenario_snapshot`.
- Идемпотентный запуск создаёт `training_session`, `simulation_workspace`,
  участников, строки `session_scheduled_card` и/или `training_call`. Для одного
  назначения может существовать только одна активная сессия.
- В одиночном сценарии workspace принадлежит одному обучаемому. Общий workspace
  содержит нескольких участников и инструктора: преподаватель запускает и
  завершает такую сессию.
- Backend рассчитывает канонический `can_complete`: все карточки плана должны
  быть выпущены без ошибок, службы участников — принять или отклонить свои
  карточки, а входящие звонки — завершиться с привязанной созданной карточкой.
  Состояние доступно через REST и realtime; раннее завершение отклоняется с
  `409` и перечнем blockers.
- Все значимые успешные и отклонённые действия сохраняются в append-only
  `training_action`. По завершении формируются `training_card_result`, общий
  балл сессии и список расхождений.
- Ручная оценка преподавателя хранится в `training_session` отдельно от
  автоматического результата: балл, итог прохождения, один общий комментарий,
  автор и время оценки. Полный снимок состояния для проверки собирается из
  read-only workspace, результатов карточек и журнала действий.
- После завершения workspace переводится в `READ_ONLY`.

- `GET /api/v1/admin/overview` — агрегированное состояние стенда;
- `GET /api/v1/admin/overview/components` — состояние источников мониторинга;
- `GET /api/v1/admin/overview/events` — последние предупреждения и ошибки;
- `GET /api/v1/admin/monitoring/metrics` — каталог разрешённых метрик;
- `GET /api/v1/admin/monitoring/metrics/current` — текущие значения;
- `GET /api/v1/admin/monitoring/metrics/{metric_key}/series` — временной ряд;
- `GET /api/v1/admin/monitoring/targets` и `/alerts` — цели и алерты Prometheus;
- `GET /api/v1/admin/logs`, `/sources`, `/export` — поиск и экспорт журналов Loki.
- `GET/POST /api/v1/admin/users` — список и создание учётных записей;
- `PATCH /api/v1/admin/users/{id}/role` и `/block` — роль и блокировка;
- `GET /api/v1/admin/reports/*` — использование, ошибки, нагрузка, доступность и
  действия пользователей;
- `GET /api/v1/admin/services`, `/backups`, `/updates` — состояние и безопасные
  заглушки потенциально опасных операций;
- `GET/PATCH /api/v1/admin/security/policy` и `GET /api/v1/admin/security/integrity` —
  парольная политика и контроль компонентов.

## SSE

Полный контракт realtime gateway — фильтры, формат конверта, все события
`card.*`, `training.*`, `stream.gap`, правила дедупликации и resync — находится
в [`src/s112/realtime_gateway/README.MD`](src/s112/realtime_gateway/README.MD).

Подключение ко всем изменениям:

```text
GET http://localhost:8081/events
```

Подключение к одной карточке:

```text
GET http://localhost:8081/events?card_id=<uuid>
```

Подключение к изменениям одного workspace:

```text
GET http://localhost:8081/events?workspace_id=<uuid>
```

Подключение преподавателя ко всем событиям его активных сессий:

```text
GET http://localhost:8081/events?teacher_id=<uuid>
```

Каждый экземпляр realtime-gateway должен иметь уникальный
`S112_REALTIME_INSTANCE_ID`: это даёт каждому экземпляру отдельную Kafka
consumer group и позволяет доставлять событие на все узлы с подключёнными
пользователями. При переполнении очереди клиент получает событие `stream.gap`
и должен перечитать карточки, план сессии и completion readiness через REST API.

## Надёжность

- запись бизнес-данных и outbox выполняется одной транзакцией;
- после сбоя worker повторяет отправку;
- `event_id` служит ключом дедупликации на стороне потребителя;
- события одной карточки блокируются более ранней неопубликованной версией;
- Kafka producer использует `acks=all` и idempotence;
- чтение с replica является eventual consistent: непосредственно после записи
  ответ изменяющего запроса является актуальнее последующего GET с реплики.
- выпуск карточки и outbox-событие фиксируются одной транзакцией;
- уникальность `(training_session_id, scenario_card_key)` защищает от повторного
  выпуска, а сбойные попытки повторяются scenario-worker с backoff;
- назначение хранит snapshot, поэтому изменение сценария или шаблона не меняет
  уже выданное задание.
- аудиофайл и запись PostgreSQL связаны компенсирующим удалением и периодической
  сверкой orphan-объектов, поскольку SeaweedFS и PostgreSQL не имеют общей
  транзакции;
- API, STT/TTS consumers и consumer результата имеют отдельные уровни
  идемпотентности; завершение сессии ждёт переноса готовой STT-расшифровки в
  журнал действий.
- семантическая проверка использует отдельные request/result topics, общий
  transactional outbox и отдельные consumer inbox; Kafka offset подтверждается
  только после сохранения результата в PostgreSQL.

## Тесты

После установки тестовых зависимостей:

```shell
python -m pip install -e ".[test]"
pytest
```

Тесты используют SQLite in-memory и не запускают Docker-сервисы. Полный
инфраструктурный smoke-test выполняется отдельно после ручного запуска Compose.

После запуска стенда базовый сценарий и сценарий сложности 2 с исходящими
звонками проверяются отдельными live-скриптами:

```shell
python tests/live_scenario_check.py
python tests/live_outbound_call_scenario_check.py
python tests/live_incoming_call_scenario_check.py
```

Во втором скрипте адрес сервера задаётся константой `SERVER_ADDRESS` в начале
файла. Скрипт использует существующий опубликованный сценарий с двумя
карточками и `evaluation_rules.outbound_call`, создаёт две отдельные попытки и
оставляет их в базе для последующего просмотра преподавателем.

Третий скрипт создаёт сценарий оператора 112 с входящим звонком и дважды
назначает его обучаемому. Реплики обучаемого генерируются `gpt-oss-20b`,
проходят через TTS и call-scoped STT API; первая итоговая карточка правильная,
во второй намеренно допущены фактические ошибки. Балл зависит только от
содержимого сохранённой карточки.

## Лицензии инфраструктурных компонентов

- Apache Kafka распространяется по лицензии Apache License 2.0. Для локального
  кластера используется legacy-образ Bitnami, конфигурация контейнера которого
  также опубликована под Apache License 2.0.
- PostgreSQL распространяется по свободной PostgreSQL License, разрешающей
  коммерческое использование, изменение и распространение. Поэтому официальный
  образ `postgres:17.11-bookworm` оставлен без изменения.
- `nvidia_gpu_exporter` распространяется по лицензии MIT и получает метрики
  через предоставляемую NVIDIA-драйвером команду `nvidia-smi`.

Это техническая проверка лицензий основных компонентов; состав базовых ОС и
включённых пакетов образов может содержать дополнительные совместимые лицензии.
Образ `bitnamilegacy/kafka:3.4` является архивным и больше не получает
обновления и поддержку Bitnami. Он подходит для зафиксированного учебного
стенда, но для production следует выбрать поддерживаемый образ и закрепить его
по digest после проверки SBOM и уязвимостей.

## Границы текущего этапа

- аутентификация и авторизация ещё не реализованы;
- запуск, остановка и перезапуск сервисов, создание и восстановление резервных
  копий, проверка и установка обновлений намеренно заблокированы для защиты
  демонстрационного стенда; попытки сохраняются в аудите;
- автоматический расчёт ЕКП и списка оповещения отсутствует, так как правила не предоставлены;
- сроки открытия карточки (30 секунд) и решения после открытия (3 минуты)
  контролируются scenario-worker; просроченное действие остаётся доступным и
  учитывается при оценке;
- Kafka настроена plaintext для локального стенда; production потребует TLS/SASL;
- переключение PostgreSQL primary/replica не автоматизировано: текущая реплика предназначена
  для read-нагрузки, а не как готовый HA-manager.
