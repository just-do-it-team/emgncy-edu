# API обучающегося и АРМ

Контракт сверён с локальным `backend/src/s112/api` и опубликованным OpenAPI
`http://78.36.74.22:8080/openapi.json` 22.09.2026. Backend не изменялся.
Назначения, карточки, звонки и дополнительные признаки обновлены по локальному student API 23.09.2026; развёрнутый контракт
повторно не проверялся.

## Запуск

- По умолчанию включён живой режим (`VITE_STUDENT_API_ENABLED=true`).
- Обучающийся входит по логину и паролю через auth-api. Идентификатор берётся
  только из профиля ответа входа; ручного ввода UUID и отдельного хранилища
  личности АРМ нет. `VITE_STUDENT_ID` больше не используется.
- Все запросы учебного API, включая справочники и аудио, идут через общий
  HTTP-клиент с `Authorization: Bearer` и `X-User-Id` из текущего профиля.
  Обязательные идентификаторы в телах запросов сохраняются по контракту backend.
  Таймаут запросов АРМ — 20 секунд. При выходе, истечении сессии или смене
  профиля запросы React Query отменяются, а кэш очищается. Ответ 401 на запрос
  текущей сессии завершает вход через общий обработчик.
- Токен и профиль хранятся в памяти: после перезагрузки требуется повторный
  вход. Ссылка на АРМ сохраняется при переходе на экран входа; после входа
  обучающегося открывается та же попытка. Контекст рабочего места загружается
  с сервера. В localStorage остаётся только ключ незавершённого запроса старта,
  отдельно для адреса API, пользователя и назначения.
- Базовый адрес `VITE_ARM_API_URL=/student-api`. В dev Vite proxy направляет его
  на `http://78.36.74.22:8080`. После изменения env требуется перезапуск dev-сервера
  пользователем. На production нужен аналогичный reverse proxy или отдельный
  адрес API с CORS; Vite proxy в production не работает.
- `VITE_STUDENT_API_ENABLED=false` возвращает прежний режим с моками.
  Ошибки живого API не заменяются моковыми данными.
- `VITE_USE_MOCKS` продолжает управлять прежними разделами и не выключается.
  Преподаватель, администратор, прогресс, материалы и старый разбор попыток
  не переводились на новый контракт.

## Подключённые операции

| Экран / действие           | API `/api/v1`                                                                                                |
| -------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Назначенные занятия        | `GET /student/scenario-assignments`, `X-User-Id`                                                             |
| Название/сложность занятия | Поле `scenario` в ответе назначения: метаданные закреплённой версии без эталонов                              |
| Состояние попыток          | `GET /training-sessions?participant_user_id=...`                                                             |
| Продолжить попытку         | `GET /student/scenario-assignments/{id}`, поле `active_session`; для старых ссылок — поиск в списке назначений |
| Начать обучение            | `POST /scenario-assignments/{id}/start`, `user_id`, `Idempotency-Key`                                        |
| Список/просмотр карточек   | `GET /workspaces/{id}/cards?limit=100&cursor=...` → `{ items, next_cursor }`, `.../cards/{id}`, `X-User-Id`   |
| Открытие ДДС               | `POST /workspaces/{id}/cards/{id}/open`                                                                      |
| Принять / отклонить        | `POST /workspaces/{id}/cards/{id}/decision`                                                                  |
| Последующее реагирование   | `POST /card-services/{id}/statuses`                                                                          |
| История реагирования       | `GET /card-services/{id}/status-history`                                                                     |
| Поля оператора 112         | `PATCH /cards/{id}`                                                                                          |
| Создание карточки         | `POST /cards`, текущие `workspace_id`, `operator_id`, `source_type=MANUAL`, поля и `features`                 |
| Учебные звонки            | `GET /training-sessions/{id}/incoming-calls`                                                                 |
| Принять / завершить звонок | `POST /incoming-calls/{id}/answer`, `.../complete`, `user_id`                                               |
| Привязать карточку        | `POST /incoming-calls/{id}/incident-card`, `user_id`, `incident_card_id`                                    |
| Классификация              | `PUT /cards/{id}/features`                                                                                   |
| Ручное добавление службы   | `POST /cards/{id}/services`                                                                                  |
| Статус карточки            | `POST /cards/{id}/statuses`, `GET /cards/{id}/status-history`                                                |
| Типы, признаки, схемы      | `GET /event-types`, иерархия `event-kinds` → `first/second/third-order-features`, `/feature-schemas/resolve` |
| Службы                     | `GET /services`                                                                                              |
| Условия завершения         | `GET /training-sessions/{id}/completion-readiness`                                                           |
| Завершение обучающимся     | `POST /training-sessions/{id}/complete` при `STUDENT_CONFIRM` и `can_complete`                               |
| Результаты                 | `GET /student/training-history` с пагинацией и `X-User-Id`                                                   |
| Аудио из сценария          | `GET /workspaces/{id}/cards/{id}/audio-messages`, `GET /audio-messages/{id}/content`                         |

Карточки, звонки и readiness обновляются каждые 5 секунд, назначения/история — каждые
15 секунд. Аудио опрашивается только при открытой панели, контент загружается
по нажатию с нужным заголовком и воспроизводится через освобождаемый Blob URL.
Голосовой диалог, запись микрофона, загрузка STT/TTS не подключены: по исходному
заданию это следующий этап. SSE необязателен для этой реализации; публичный URL
отдельного gateway не задан, поэтому используется REST polling.

## Целостность и поведение

- На входе обоих режимов — список карточек, затем просмотр выбранной карточки.
- В АРМ 112 доступно создание карточки участником текущего workspace. Категория,
  описание, адрес, количество пострадавших, анкета и классификация отправляются
  одним POST; после создания открывается редактор карточки. Категория после
  создания неизменяема. Пока открыта форма или выполняется действие со звонком,
  ручное завершение занятия заблокировано.
- Панель звонков показывает PENDING/RINGING/ACTIVE/COMPLETED/FAILED/CANCELLED.
  Принять можно только RINGING, привязать карточку — к ACTIVE, завершить — ACTIVE
  с привязанной карточкой. FAILED/CANCELLED требуют обращения к преподавателю;
  фронтенд не обходит серверные условия завершения.
- Создание и привязка — отдельные операции. После успешного создания ID остаётся
  в списке выбора даже до обновления проекции карточек. Если привязка не прошла,
  можно повторить только её. После перезагрузки ранее созданная карточка выбирается
  из загруженного списка по номеру и адресу; следующие страницы доступны через
  «Загрузить ещё». Перед привязкой проверяется operator_id, а сервер дополнительно
  запрещает карточки сценария и повторное использование карточки другим звонком.
- Создание карточки не имеет гарантии идемпотентности. При таймауте или 5xx
  повторная отправка из этой формы блокируется: нужно закрыть её, обновить список
  и проверить наличие карточки. Автоматического повторного POST нет.
- Данные загружаются только в контексте назначений/рабочего места обучающегося.
  Общий `GET /cards` не используется.
- Список карточек загружается по 100 записей; кнопка «Загрузить ещё» передаёт
  непрозрачный `next_cursor` без изменения. Первая страница запрашивается без
  cursor. `next_cursor=null` означает конец списка; общее количество API не
  возвращает, поэтому интерфейс показывает число загруженных карточек.
  Автообновление и ручное обновление перечитывают уже загруженные страницы
  последовательно с начала, используя новые курсоры. Дубли удаляются по
  `card_id`, при повторе сохраняется запись с большей версией. Ошибка загрузки
  следующей страницы не очищает список; её можно повторить.
- Назначения содержат `scenario`, текущего `participant` и `active_session`.
  Отдельный запрос преподавательского сценария для строк таблицы удалён.
  API-клиент также поддерживает `GET /student/scenario-assignments/{id}`.
  Число использованных попыток и блокировка по `max_attempts` пока вычисляются
  по `GET /training-sessions?participant_user_id=...`: student-назначение
  возвращает только номер активной попытки, а не общее число попыток.
- Запуск: ключ идемпотентности сохраняется **до POST**. При потерянном ответе
  сначала перечитывается назначение: если сервер уже возвращает активную попытку,
  открывается она; иначе повтор POST использует тот же сохранённый ключ.
  Ключ удаляется после успешного ответа старта или подтверждения активной попытки.
- Продолжение: рабочее место, участник и название берутся из student endpoint,
  сохранённый `LaunchContext` больше не читается и не записывается. Новая ссылка
  содержит `assignment`, `session` и выбранный `mode`; старые ссылки с одним
  `session` восстанавливаются через список назначений. Режим интерфейса не меняет
  права и назначенную службу. При отсутствии mode он определяется по position_code.
- Открытие ссылки выполняет только GET: новая попытка не создаётся. При задержке
  репликации выполняются до трёх повторов GET через 1,5 секунды; затем доступны
  ручной повтор, список занятий и результаты. Другую активную попытку вместо
  указанной в ссылке frontend не открывает. Завершённые попытки не восстанавливаются
  через active_session; их результаты доступны в истории.
- Записи карточки/признаков/служб содержат актуальную `expected_version` или
  `expected_card_version`, actor/author UUID и `request_id`. Request ID журнала
  не считается гарантией идемпотентности. Записи автоматически не повторяются.
- PATCH и PUT признаков — две серверные операции. После PATCH используется
  возвращённая версия; после PUT перечитывается карточка со службами. При
  частичном успехе интерфейс сообщает, что уже сохранено. При конфликте или
  неизвестном результате требуется обновление перед следующей записью; форма
  сохраняет введённые данные. Изменения других участников не затирают черновик.
- ДДС изменяет только свою назначенную службу (`position_code`). Принятие и отказ
  идут через student decision endpoint, не через общий endpoint статусов.
  Переходы взяты из `domain/rules.py`; отказ требует комментария. Для 103 не
  предлагаются REJECTED/WORK_REFUSED. История остальных служб доступна для чтения.
- Завершённые сессии и недоступное readiness блокируют запись. Решение о возможности
  завершения принимает сервер; режимы AUTO_WHEN_READY и TEACHER_ONLY учитываются.
- Адрес и описание записываются в `incident_address` и `description`.
  Анкета соответствует `CardQuestionnaire`: `null` или объект только с двумя
  строками `questions` и `answers`. Оператор 112 редактирует вопросы и ответы,
  ДДС просматривает их. Переносы строк сохраняются; пустая исходная анкета
  остаётся `null`, если вопросы и ответы не заполнены. Дополнительные ключи,
  включая прежний `operator112`, больше не отправляются. Отдельных полей
  для ФИО, статуса заявителя и телефонов в текущем API нет, поэтому в форме
  оператора 112 с подключённым API они скрыты и не участвуют в валидации.
  Адрес в этом режиме вводится целиком, без добавления страны и города
  по умолчанию. Демонстрационная форма сохраняет прежние поля и проверки.
- Живые справочники используют только серверные ID. Моковый JSON-классификатор
  никогда не используется для формирования запросов к серверу.

## Ограничения текущего бэкенда

1. `create_card` разрешён INSTRUCTOR и PARTICIPANT активного учебного workspace.
   АРМ 112 создаёт карточки от текущего обучающегося. Для привязки к учебному звонку
   сервер требует карточку этого обучающегося, не выпущенную сценарием.
2. Нет ARM112/DDS в назначении: `position_code` — код службы. Интерфейс выбирается
   в таблице занятий, по умолчанию DDS при назначенной службе, иначе ARM112.
   Выбор интерфейса не изменяет назначение и серверные права.
3. PATCH не поддерживает `event_type_id`, а PUT features проверяет принадлежность
   event kind этой категории. Доступны типы внутри категории исходной карточки.
4. Нет endpoint предварительного расчёта служб. В футере показаны службы
   сохранённой карточки; после сохранения признаков получаем расчёт сервера.
5. `TrainingSessionResponse` не содержит `workspace_id`. Для продолжения теперь
   используется `active_session` student endpoint, в том числе после входа
   на другом устройстве и при запуске преподавателем. Локальная запись контекста
   больше не требуется.
6. Кабинет обучающегося больше не запрашивает `GET training-scenarios/{id}`:
   безопасные метаданные приходят вместе с назначением. Полное описание сценария
   и эталоны не загружаются этим запросом.
7. Список workspace/cards использует cursor-пагинацию; ограничение API в 500
   относится к одной странице. Фронтенд запрашивает по 100 карточек и позволяет
   загружать следующие страницы без прежнего общего ограничения в 500 записей.
8. Дополнительные признаки проверяются по серверной схеме: string, boolean,
   number, integer, enum, required и additionalProperties=false. Очистка
   необязательного поля удаляет ключ; false и 0 сохраняются. Boolean имеет
   три состояния: не задано / да / нет. Обязательная строка может быть пустой,
   если ключ присутствует: это соответствует проверке backend. Значение enum
   сохраняет исходный тип. Устаревшие ключи не удаляются молча: показывается
   действие удаления, а запрещённые схемой ключи блокируют сохранение.

## Проверка

Короткие команды без сборки и dev-сервера:

```sh
node node_modules/typescript/bin/tsc --noEmit --project tsconfig.app.json
node node_modules/typescript/bin/tsc --noEmit --project tsconfig.node.json
npm run lint
```

Для полной приёмки нужна учётная запись student с назначением. Проверить вход,
выход, истечение сессии, обработку 401, смену пользователя, запуск, повторный вход
после reload и возврат по URL с session, получение карточки, сохранение 112, реагирование
ДДС, конфликт версии, создание карточки, цикл звонка «принять → создать → привязать
→ завершить», повтор привязки после сбоя, очистку дополнительных признаков и
завершение занятия. Живые изменения не проверялись без выбранного
пользователем тестового обучающегося.
