# Аутентификация и авторизация

Статус: реализовано — все четыре ручки есть; расхождения с описанным ниже целевым
контрактом перечислены у каждой ручки
Потребитель на фронте: `features/auth`, `entities/session`, `app/providers/router`, `app/providers/configure-api`
Связанные файлы фронта: `frontend/src/features/auth/api/endpoints.ts`, `frontend/src/features/auth/api/login.ts`, `frontend/src/entities/session/model/session.ts`, `frontend/src/entities/session/model/token.ts`, `frontend/src/entities/session/model/use-session-expiry.ts`, `frontend/src/app/providers/configure-api.ts`, `frontend/src/app/providers/configure-session.ts`

## Назначение

Появился отдельный сервис `auth-api` на порту 8084: он проверяет пароль существующей записи
`user_account`, обновляет `last_login_at` и выпускает подписанный JWT. Фронт на него переведён:
демо-учётки удалены, роль приходит с сервера, токен уходит заголовком.

Реализованы все четыре ручки: `login`, `profile`, `refresh`, `logout`. Схема отличается от
целевой: refresh-токена и cookie нет, продление работает как скользящее окно поверх того же
access-токена. Проверка токена на card-api и admin-api включается флагом `S112_AUTH_ENABLED`
и по умолчанию выключена, поэтому личность по-прежнему идёт в `X-User-Id` и подделывается
тривиально.

Без этого контракта не существует: RBAC на всех трёх уровнях, разделения кабинетов, аудита
с достоверным актором, изоляции рабочих пространств обучаемых, соответствия 152-ФЗ.

## Ручки

### POST /api/v1/auth/login

Статус: **реализовано** на `auth-api`, порт 8084.
Назначение: вход по логину и паролю, выдача access-токена и установка refresh-cookie.
Отношение к существующему: реализованная ручка расходится с этим разделом — расхождения
перечислены сразу после примера ответа.
Доступ: без авторизации.

Тело запроса:

| Поле | Тип | Обязательно | Ограничения | Описание |
|---|---|---|---|---|
| `username` | string | да | 1..64, trim | логин |
| `password` | string | да | 1..128 | пароль |

Успешный ответ: 200

| Поле | Тип | Описание |
|---|---|---|
| `access_token` | string | JWT, живёт в памяти фронта |
| `token_type` | string | `bearer` |
| `expires_in` | int | срок жизни access в секундах |
| `expires_at` | datetime | момент истечения; **источник срока жизни для клиента** |
| `user` | object | профиль, см. `GET /auth/profile` |

Клиент берёт срок жизни из `expires_at`, а не из payload токена: JWT на фронте не
разбирается и библиотека разбора не подключается. `expires_in` используется только как
запасное значение, если `expires_at` не разбирается как дата.

Дополнительно устанавливается refresh-cookie: `httpOnly`, `Secure`, `SameSite=Strict`,
`Path=/api/v1/auth`. Значение refresh фронту недоступно и в теле ответа не передаётся.

Пример ответа:

```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type": "bearer",
  "expires_in": 900,
  "user": {
    "id": "0f6b2d1e-8a44-4c2e-9d3f-1c77b0a5e412",
    "username": "smirnova.ea",
    "display_name": "Смирнова Елена Андреевна",
    "role": "teacher",
    "is_blocked": false,
    "last_login_at": "2026-09-20T09:12:41+03:00"
  }
}
```

Ошибки:

| Код | Когда | Тело |
|---|---|---|
| 401 | неверный логин или пароль | `{"detail": "Неверный логин или пароль"}` |
| 403 | учётная запись заблокирована | `{"detail": "Учётная запись заблокирована"}` |
| 422 | валидация | `{"detail": [{"loc": ["body", "username"], "msg": "...", "type": "..."}]}` |
| 429 | превышен лимит попыток | `{"detail": "Слишком много попыток входа"}` |

Ответ на неверный логин и на несуществующего пользователя обязан быть неразличим.

Реализованная ручка отличается от описанного выше:

| Что | В контракте | Как реализовано |
|---|---|---|
| refresh-cookie | ставится в ответе | **не ставится**, refresh не существует |
| `role` | `admin` \| `teacher` \| `student` | `ADMINISTRATOR` \| `TEACHER` \| `STUDENT` |
| `expires_in` | 900 с | 3600 с, настраивается `S112_AUTH_ACCESS_TOKEN_TTL_SECONDS` |
| `email` в профиле | не описан | присутствует |
| 429 при переборе | описан | лимита попыток нет |
| Порт | общий с card-api | отдельный сервис 8084 |

Регистр роли приводится явным преобразователем `roleFromApi`
(`frontend/src/features/auth/api/login.ts`), а не приведением регистра по месту:
неизвестная роль — отказ во входе, а не молчаливое падение в `student`.

### POST /api/v1/auth/refresh

Статус: **реализовано**, но иначе (`backend/src/s112/auth/api.py:109-142`).
Назначение: выдать новый access-токен взамен предъявленного.
Доступ: **по действующему access-токену** в заголовке `Authorization: Bearer`, а не по
cookie. Проверка выполняется всегда, независимо от `S112_AUTH_ENABLED`.
Тело запроса: пустое.

Успешный ответ: 200 — формат `login` целиком, включая `user`. Предъявленный токен
немедленно отзывается: его `jti` записывается в `revoked_access_token` вместе с исходным
`expires_at` (миграция `0011`).

Ошибки:

| Код | Когда | Тело |
|---|---|---|
| 401 | токен отсутствует, истёк, повреждён или уже отозван | `{"detail": "Access token has been revoked"}` |
| 403 | учётная запись заблокирована | `{"detail": "..."}` |

Отличия от целевого контракта: cookie не участвует, ротации refresh нет — ротируется сам
access. Следствие описано в «Ограничениях текущей схемы».

### POST /api/v1/auth/logout

Статус: **реализовано** (`backend/src/s112/auth/api.py:145-170`).
Назначение: отозвать предъявленный access-токен.
Доступ: по действующему access-токену. Тело запроса пустое.

Успешный ответ: 204 без тела. `jti` токена записывается в `revoked_access_token`.

Ошибки: 401 — токен отсутствует, истёк или уже отозван. **Ручка не идемпотентна**:
повторный вызов с тем же токеном отвечает 401, а не 204, потому что токен уже в списке
отозванных. Cookie не очищается — её нет.

### GET /api/v1/auth/profile

Статус: **реализовано** (`backend/src/s112/auth/api.py:95-104`).
Назначение: профиль текущего пользователя.
Доступ: по действующему access-токену, независимо от `S112_AUTH_ENABLED`. Профиль берётся
по `sub` из актуальной записи `user_account`, поэтому смена роли и блокировка применяются
без ожидания истечения токена.

Возвращается тот же объект `user`, что и в ответе `login`, с дополнительными полями
`email`, `created_at`, `updated_at`.

Успешный ответ: 200

| Поле | Тип | Описание |
|---|---|---|
| `id` | uuid | идентификатор пользователя |
| `username` | string | логин |
| `display_name` | string | ФИО для отображения |
| `role` | string | `admin` \| `teacher` \| `student` |
| `is_blocked` | bool | признак блокировки |
| `last_login_at` | datetime \| null | последний вход |

Ошибки: 401 — токен отсутствует или истёк.

## Ограничения текущей схемы

Раздел описывает то, что на фронте сделать нельзя, пока бэкенд не закроет пункты из
«Требуется на бэкенде». Это не список недоработок фронта: каждый пункт — следствие
отсутствующей возможности, и обходить его на клиенте запрещено.

**Проверка токена на бэкенде выключена.** `S112_AUTH_ENABLED` по умолчанию `false`
(`backend/src/s112/auth/settings.py:13`), поэтому card-api не смотрит на `Authorization`
вообще, а личность берётся из `X-User-Id`, `teacher_id` и `assigned_by` — заголовков и
полей, которые подделываются подстановкой чужого UUID. Заголовок `Authorization` фронт
отправляет всё равно: при включении флага менять на клиенте не придётся ничего.
**Блокирующее для промышленной эксплуатации:** до включения проверки разграничения доступа
не существует, любой обучаемый читает данные любого другого, и требования 152-ФЗ
не выполняются.

**Продление — скользящее окно, а не refresh-токен.** `POST /auth/refresh` требует
**действующий** access-токен: `principal: Principal = Depends(get_current_principal)`
(`backend/src/s112/auth/api.py:108`). Отсюда два следствия, которые определяют поведение
клиента. Первое: продлевать нужно **заранее**, до истечения `expires_at`, а не по факту
первого 401. Второе: если срок истёк, предъявлять для обмена нечего — **сессия
невосстановима**, пользователь проходит полный вход заново. Промежуточного состояния
«access протух, refresh жив» в этой схеме не существует.

**Перезагрузка страницы по-прежнему уводит на вход.** `GET /auth/profile` появился, но сам
по себе задачу не решает: чтобы его вызвать, нужен токен, а токен живёт только в памяти
вкладки и после F5 не существует. Предъявлять ручке нечего.

Обходить это сохранением access-токена в `localStorage`, `sessionStorage`, IndexedDB или
persist-хранилище **запрещено и останется запрещённым**: любой XSS выносит действующую
сессию целиком, а срок жизни токена — час. Так же запрещено сохранять профиль: роль в нём
правится через DevTools за десять секунд, и клиент начнёт считать себя преподавателем без
единого запроса к серверу.

Решается это на стороне бэкенда: refresh-токен в `httpOnly; Secure; SameSite=Strict`
cookie, которую браузер предъявляет автоматически и которую JavaScript прочитать не может.
После F5 клиент делает один запрос на обмен, получает access в память и профиль вместе с
ним. До появления такой cookie экран входа после перезагрузки — осознанная цена, а не
дефект.

## Решения фронта, зафиксированные при интеграции

| Решение | Причина | Когда пересматривается |
|---|---|---|
| Токен только в памяти, в замыкании модуля `entities/session/model/token.ts` | ни `localStorage`, ни `sessionStorage`, ни persist-хранилище, ни React-состояние: XSS выносит сессию целиком, а состояние видно в devtools | не пересматривается |
| Токен уходит одним способом — `Authorization: Bearer` в request-интерцепторе единственного axios | ни в URL, ни в теле, ни в query: URL попадает в историю браузера, логи прокси и Referer | не пересматривается |
| JWT на клиенте не разбирается | payload токена не является источником решений; библиотека разбора — лишняя зависимость без выигрыша | не пересматривается |
| `withCredentials: false` | куки не используются, токен идёт заголовком | при переходе на refresh в `httpOnly`-куке переключается на `true`. CORS этому больше не мешает: все четыре сервиса отдают конкретные origin `http://localhost:5173` и `http://127.0.0.1:5173` вместо `*` |
| Гард маршрутов — удобство, а не защита | роль приходит с клиента и клиентом же проверяется; ограничение ролей обязано проверяться на сервере, гард лишь прячет то, что сервер всё равно не отдаст | не пересматривается |
| Личность имеет один источник — профиль из ответа входа | идентификатор обучаемого в сторе АРМ переживает перезагрузку, а сессия нет; без сброса возникает состояние «токена нет, но АРМ считает, что знает пользователя» | снимается вместе с `GET /auth/profile` |

## Требования к авторизации на существующих ручках

Дельта к уже реализованному API, а не новые ручки:

- Все ручки card-api и admin-api, кроме `/health`, требуют `Authorization: Bearer <access>`.
- `X-User-Id` на `GET /api/v1/workspaces/{id}/cards` и `.../{card_id}` перестаёт быть источником личности: личность берётся из токена, заголовок удаляется из контракта.
- Ручки тренажёра ограничиваются по роли: создание и правка сценариев, назначения, ручной вброс карточки и завершение сессии — `teacher` и `admin`; `student` видит только свои назначения и сессии.
- admin-api целиком доступен только роли `admin`; бинд на 127.0.0.1 перестаёт быть единственной защитой.
- `X-Admin-Actor-Id` и `X-Admin-Actor-Username` в аудите заменяются на актора из токена: сейчас они пишутся без проверки и позволяют подделать запись аудита.
- SSE-подключение `GET :8081/events` авторизуется и ограничивается видимостью: обучаемый получает события только своего рабочего пространства.

## Связанные SSE-события

| Событие | Когда | Полезная нагрузка | Что делает фронт |
|---|---|---|---|
| `session.revoked` | администратор заблокировал пользователя или отозвал сессию | `{user_id, reason}` | немедленный logout, очистка кэша, редирект на вход |

## Кэшируемость

`GET /auth/profile` — класс «полусправочники»: `staleTime` 5 мин, инвалидация при `login`,
`logout` и `session.revoked`. Access-токен не кэшируется и не персистится нигде.

## Сессия

| Параметр | Предложение фронта | Решает бэкенд |
|---|---|---|
| Срок жизни access | 15 мин | да |
| Срок жизни refresh | 24 ч, без продления сверх суток | да |
| Автовыход по неактивности | 30 мин | да |
| Жёсткий предел сессии | 24 ч с момента входа | да |
| Лимит попыток входа | 5 за 15 мин на пару логин + IP | да |

Пороги приходят с бэка (в профиле или отдельной ручкой), чтобы фронт не дублировал константы.

## Открытые вопросы

0. **Блокирующий для промышленной эксплуатации.** Когда включается `S112_AUTH_ENABLED`?
   Пока флаг выключен, `Authorization` не проверяется, личность идёт в `X-User-Id` и
   подделывается, разграничения доступа не существует. Фронт к включению готов: заголовок
   отправляется уже сейчас, менять на клиенте нечего. Нужны дата и порядок включения,
   потому что после него все ручки без токена начнут отвечать 401.
1. Где хранится refresh: таблица сессий в PostgreSQL или подписанная cookie без состояния. Предпочтение фронта — таблица: без неё невозможен принудительный отзыв сессии администратором.
2. Двухфакторная аутентификация: требуется ли на текущем этапе. В ТЗ прямого требования нет, но для роли `admin` она напрашивается. Если да — нужен отдельный шаг контракта (`POST /auth/login` возвращает `challenge_id` вместо токена).
3. Отдавать ли пороги сессии в `GET /auth/profile` или отдельной ручкой `GET /auth/policy`.
4. Нужен ли отдельный эндпоинт для смены пароля пользователем или это остаётся операцией администратора (`admin-api` уже умеет создавать пользователя, но не менять пароль).
5. Совпадает ли `user.id` из профиля с `X-User-Id`, который сейчас ожидают workspace-ручки, и с `actor_id` в аудите.

## Требуется на бэкенде

| Приоритет | Что реализовать | Блокирует |
|---|---|---|
| P0 | Включение `S112_AUTH_ENABLED` и проверка `Authorization: Bearer` на всех ручках card-api и admin-api | RBAC, изоляция данных обучаемых, 152-ФЗ. Сейчас личность идёт в `X-User-Id` и подделывается |
| P0 | Refresh-токен в `httpOnly; Secure; SameSite=Strict` cookie и обмен по ней | перезагрузка страницы выбрасывает на экран входа; продление сейчас требует живого access-токена, после истечения сессия невосстановима |
| P0 | Серверная проверка роли по операциям (кто может править сценарий, вбрасывать карточку, завершать сессию) | кабинеты преподавателя и администратора |
| P1 | Идемпотентный `POST /auth/logout` | повторный вызов сейчас отвечает 401, а не 204 |

| P1 | Чтение SSE с заголовком `Authorization` без `EventSource` | подключение к `/events` авторизуется, но браузерный `EventSource` заголовки не поддерживает — см. `docs/api/realtime.md` |

| P2 | Пороги сессии, отдаваемые фронту | дублирование констант на клиенте |
| P2 | 2FA для роли `admin` | решается вопросом 2 |
