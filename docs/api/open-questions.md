# Открытые вопросы к бэкенду

Статус: черновик
Потребитель на фронте: весь фронтенд
Связанные документы: `docs/api/auth.md`, `docs/api/realtime.md`, `docs/api/attempts.md`,
`docs/api/lessons.md`, `docs/api/scenarios.md`

Сводный список вопросов, которые не привязаны к одной функциональной области либо
блокируют сразу несколько. Вопросы по конкретной области живут в её документе; здесь —
то, что требует решения бэкендера и без чего фронт не может двигаться дальше.

Каждый пункт описывает **фактическое состояние**, а не пожелание. Проверено по коду
на 24.09.2026.

## 1. Чем строится блок дополнительных признаков опросной карты

Приоритет: P0.

`GET /api/v1/feature-schemas/resolve` удалена. Миграция `0013_remove_feature_schema.py`
сносит таблицу `feature_schema` (строка 75), убирает `feature_schema_id` из `card_feature`,
`card_feature_history` и `service_routing_rule` (строки 45, 46, 55) и переводит
маршрутизацию служб на `service_routing_rule.event_kind_id` (строка 56). Поле
`additional_features_schema` в ответах API не встречается ни разу.

Фронт ручку всё ещё зовёт: `frontend/src/entities/training/api/training-api.ts:374`.
Ответ `404` глушится и превращается в `null` (строка 386), поэтому падения нет — блок
дополнительных признаков просто никогда не строится.

**Вопрос.** Чем теперь задаётся набор дополнительных признаков для выбранной цепочки
ЕКП? Варианты, которые видит фронт: новая ручка вместо удалённой; схема в составе
`event-kinds`; отказ от дополнительных признаков как таковых. Предпочтение фронта —
первое: опросная карта по правилам домена строится из дерева ЕКП, а не пишется руками,
и без схемы построить её нечем.

## 2. Проверка токена на бэкенде выключена

Приоритет: P0, блокирующее для промышленной эксплуатации.

`S112_AUTH_ENABLED` по умолчанию `false` (`backend/src/s112/auth/settings.py:13`).
card-api и admin-api заголовок `Authorization` не проверяют, личность берётся из
`X-User-Id`, `teacher_id` и `assigned_by` — они подделываются подстановкой чужого UUID.
Разграничения доступа не существует: любой обучаемый читает данные любого другого.

Фронт к включению готов — заголовок отправляется уже сейчас, менять на клиенте нечего.

**Вопрос.** Когда флаг включается и в каком порядке? После включения все запросы без
токена начнут получать `401`, поэтому нужна согласованная дата: фронт и бэк переключаются
одновременно. Подробности — `docs/api/auth.md`, раздел «Ограничения текущей схемы».

## 3. Нормативы времени — вопрос закрыт

`CARD_OPEN_DEADLINE_SECONDS = 30` и `CARD_DECISION_DEADLINE_SECONDS = 180`
заданы бизнес-требованиями. Преподаватель их не меняет; хранение настроек
нормативов в сценарии или назначении не требуется.

## 4. Что считать занятием — вопрос закрыт

В проекте занятие называется **сценарием** (`training_scenario`). Сценарий
назначается обучаемым через `scenario_assignment`, группе — через
`assignment_batch`; `training_session` хранит попытку. Отдельная сущность
`lesson` и маршруты `/lessons` не планируются. Сводка результатов по группе,
если потребуется, должна относиться к конкретному назначению сценария группе.

## 5. Нет ручки, отдающей исходное аудио реплики обучаемого

Приоритет: P1.

Наружу отдаются только TTS-сегменты заявителя:
`GET /api/v1/tts-segments/{segment_id}/content` и
`GET /api/v1/audio-messages/{message_id}/tts-segments`. Загруженная обучаемым запись
попадает в SeaweedFS и в `audio_message`, но ручки, возвращающей её байты по
идентификатору сообщения STT, в API нет — `GET /api/v1/audio-messages/{id}/content`
существует, однако разбор попытки требует связать запись с действием и временем.

Без этого преподаватель не может прослушать, что именно сказал обучаемый, а домен
требует раскрывать балл по пути «итог → критерий → поле → номер действия и секунда
записи».

**Вопрос.** Планируется ли выдача исходного аудио в контексте разбора попытки и в каком
виде — потоком по сообщению или списком на сессию с таймкодами?

## 6. Записи голоса обучаемых — персональные данные

Приоритет: P1.

Запись голоса — биометрический персональный признак. В контуре хранятся: аудиофайл в
SeaweedFS, расшифровка в `audio_message.transcript`, действие
`AUDIO_MESSAGE_TRANSCRIBED` в `training_action`. Срок хранения, правила доступа и порядок
удаления нигде не определены; `audio-reconciler` удаляет только объекты-сироты, у которых
нет записи в `audio_message`, то есть к сроку хранения отношения не имеет.

ТЗ требует хранения журналов не менее 6 месяцев, но это про журналы, а не про биометрию,
и 152-ФЗ для последней строже.

**Вопрос.** Какой срок хранения записей и расшифровок, кто имеет к ним доступ помимо
преподавателя назначения, предусмотрено ли удаление по запросу субъекта и отражено ли это
в аудите? До ответа фронт не строит экранов с постоянным доступом к архиву записей.

## 7. ФИО участника в контексте экспертной оценки

Приоритет: P1.

`GET /api/v1/training-sessions/{id}/expert-review-context` отдаёт участников только
идентификаторами (`participant_ids`), назначение `GET /teacher/scenario-assignments/{id}` —
тоже (`participants[].user_id`). Имя экран разбора берёт из `GET /api/v1/students`,
загружая список обучаемых преподавателя целиком и строя карту идентификатор → ФИО.
Поиска по идентификатору у ручки нет. Обучаемый, которого в этом списке нет (например,
удалённый из всех групп преподавателя), показывается сокращённым идентификатором.

**Вопрос.** Можно ли отдавать в `expert-review-context` участников объектами
`{user_id, display_name, participant_role}`? Это закрывает и имя, и роль: сейчас роль
приходится брать вторым запросом к назначению. Предпочтение фронта — да, поле
`participants` рядом с `participant_ids`.

## 8. Занятие и попытка как отдельные ручки — вопрос закрыт

Расхождение закрыто. Ручек `/api/v1/lessons…` и `/api/v1/…/attempt…` на бэкенде нет и не
будет: занятие — это назначенный сценарий (пакет назначений `assignment_batch_id`), попытка —
тренировочная сессия. Кабинет преподавателя переведён на существующие ручки:
`/scenario-assignments`, `/learning-groups`, `/teacher-monitoring/sessions`,
`/training-scenarios`, `/students`. Выдуманный слой занятий удалён, `docs/api/lessons.md` и
`docs/api/attempts.md` переписаны.

Остался долг: старый экран разбора `/teacher/attempts/{attempt_id}` и слой `entities/attempt`
работают на моках. Новый разбор `/teacher/attempts/{session_id}/review` работает на
`expert-review-context`. Два экрана разбора существуют параллельно, пока старый не переведён на
`expert-review-context.cards[].current_state` против `expected_result`.

## 10. Исходящий звонок ДДС в разборе попытки

Исходящий звонок диспетчера ДДС хранится как `training_call` с `direction = OUTBOUND`, но в
`expert-review-context` элемента для него нет: `incoming_calls[]` фильтруется по `INBOUND`, а
реплики приходят в `call_utterances[]` без привязки к элементу. Запись для `OUTBOUND` сервер
не отдаёт (404).

Сейчас фронт строит элемент «Исходящий звонок N» из `call_utterances[]` по `call_id` и из
действий `OUTGOING_CALL_STARTED` / `OUTGOING_CALL_COMPLETED`. Реплики показываются на шкале
засечками от начала звонка; если действия начала нет — от начала попытки, с пояснением.
Статуса звонка, длительностей реплик и результата проверки по звонку нет.

Предложение: массив `outgoing_calls[]` в контексте и запись исходящего звонка. Контракт — в
`attempt-replay.md`.

Вопросы, от которых зависит конструктор:

| Приоритет | Вопрос | Что сейчас на фронте |
|---|---|---|
| P1 | Проверка владельца в PATCH и DELETE сценария, DELETE шаблона: правит и архивирует только автор | действия над чужим сценарием скрыты на клиенте по `created_by`; сервер их выполнит, если отправить запрос напрямую |
| P1 | Снятие утверждения: `PUBLISHED → DRAFT` без активных назначений или копия со связью | кнопки нет; при утверждении предупреждаем, что снять его нельзя, для правок — копия |
| P1 | Аудит утверждения и архивирования с обязательной причиной | причину не спрашиваем: отправить её некуда, аудит пишется только по заголовкам admin-api |

| P1 | Единая семантика `null`: у встроенной карточки — «не проверяется», у шаблона — «должно быть пустым» | режим проверки поля вычисляется по источнику элемента |
| P1 | Критерии успешности сценария (`pass_threshold`) | зачёт — только при нуле расхождений |
| P1 | `target_roles` и `used_in_assignments` в списке сценариев | роль выводится по составу; использование — только по своим назначениям |
| P1 | Закрытый список `action_type` для условия «после действия» | неизвестный код показывается с пометкой «названия нет» |

| P2 | Имя автора сценария и шаблона (`created_by_name`) в списке и карточке | колонка «Автор» показывает «Вы» или «Другой преподаватель» |
