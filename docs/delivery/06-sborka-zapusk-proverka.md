# 6. Сборка, запуск и проверка

Раздел отвечает на требования ТЗ, разд. 13 и 9: инструкции по компиляции, сборке и установке, процедуры установки, настройки и восстановления. Исходный код открыт и не обфусцирован: фронтенд — `frontend/` (TypeScript), бэкенд — `backend/` (Python, C++-воркер синтеза речи — `backend/tts-worker/`).

## 6.1. Требования к машине

Таблица 32 — Требования к серверу

| Ресурс | Требование |
|---|---|
| ОС | Linux с Docker Engine и Docker Compose v2 |
| GPU | NVIDIA с драйвером и NVIDIA Container Toolkit — обязательно для speech-api. Сборка по умолчанию под архитектуру CUDA 7.5 (RTX 2060 и новее); для другой карты задаётся `CUDA_ARCHITECTURES` |

| Сеть | Доменное имя, указывающее на сервер, если нужен сертификат Let's Encrypt |

Рабочее место обучаемого:

- экран от 1440 px по ширине рекомендуется для АРМ, кабинеты работают и на узком экране;
- гарнитура с микрофоном. Браузер даёт доступ к микрофону только по HTTPS или с `localhost`.

## 6.2. Подготовка сервера и переменные окружения

1. Установить Docker Engine, Docker Compose v2, драйвер NVIDIA и NVIDIA Container Toolkit.
2. Разместить модели в каталоге моделей (по умолчанию `backend/models`); в репозиторий и образы они не входят:
   - `GigaAM-v3-e2e-rnnt/` — распознавание речи;
   - `Qwen3-TTS-12Hz-0.6B-Base-Q8_0.gguf` и `mmproj-Qwen3-TTS-12Hz-0.6B-Base-F16.gguf` — синтез;
   - `refs/` — референсы голосов.
3. Запустить llama-server с моделью gpt-oss-20b на хосте, например `--host 0.0.0.0 --port 4555`.
4. Заполнить переменные окружения по образцам.

Таблица 33 — Файлы переменных окружения

| Файл | Образец | Основные переменные |
|---|---|---|
| `backend/.env` | `backend/.env.example` | Пароли PostgreSQL и репликации; адреса публикации портов; `AUTH_ENABLED`, `AUTH_JWT_SECRET` (не короче 32 байт), срок жизни токена; параметры Kafka, SeaweedFS, речи (`SPEECH_MODELS_DIR`, `TTS_DEFAULT_VOICE_ID`, `CUDA_ARCHITECTURES`, `S112_STT_*`, `S112_TTS_*`); адрес и модель LLM (`S112_DIALOGUE_LLM_*`, `S112_SEMANTIC_EVALUATION_*`); пароль Grafana |
| `frontend/.env` | `frontend/.env.example` | Относительные адреса API (`/student-api`, `/auth-api`, `/realtime-gateway`, `/admin-api`), флаги моков. Переменные `VITE_*` встраиваются при сборке; `VITE_*_PROXY_TARGET` использует только dev-сервер |
| `.env` в корне | `.env.example` | `DOMAIN` и `CERTBOT_EMAIL` для сертификата; при необходимости `ROOT_SPEECH_MODELS_DIR` |

Пароли и секреты в образцах — заглушки, при установке их нужно заменить.

Модуль журналов admin-api (`backend/src/s112/admin_api/logs/`) не входит в репозиторий: его исключает правило `logs/` в `.gitignore`, а `admin_api/main.py` его импортирует. Из чистой копии репозитория admin-api не запустится, пока модуль не добавлен (раздел 8).

## 6.3. Полный стенд с TLS: корневой `docker-compose.yaml`

Поднимает бэкенд, наблюдаемость и nginx с фронтендом. Наружу открыты только порты 80 и 443, авторизация на сервисах включена.

```shell
docker compose --env-file frontend/.env --env-file backend/.env --env-file .env up -d
docker compose --env-file frontend/.env --env-file backend/.env --env-file .env --profile tls run --rm certbot
docker compose --env-file frontend/.env --env-file backend/.env --env-file .env restart nginx
```

- До выпуска сертификата nginx отвечает 503 на всё, кроме проверки домена.
- Продление сертификата: `... --profile tls run --rm certbot renew`, затем `... exec nginx nginx -s reload`. Обе команды нужно поставить в расписание.
- Миграции БД выполняет одноразовый сервис `migrate` при старте.
- Метрики GPU включаются профилем `gpu`.
- После изменения переменных `VITE_*` образ nginx пересобирается.

## 6.4. Локальный запуск

**Бэкенд без nginx и TLS** (`backend/compose.yaml`). Порты сервисов публикуются на адреса из `backend/.env`, по умолчанию `127.0.0.1`. Авторизация по умолчанию выключена (`AUTH_ENABLED=false`).

```shell
cd backend
cp .env.example .env        # заменить пароли
docker compose --env-file .env up -d --build
```

**Фронтенд в режиме разработки** (Node.js 22.6 или новее, npm):

```shell
cd frontend
cp .env.example .env
npm ci
npm run dev                 # http://localhost:5173
```

Адреса API в `.env` относительные, dev-сервер Vite проксирует их на `VITE_*_PROXY_TARGET` (`frontend/vite.config.ts`). Пока цель пуста, прокси не регистрируется и запросы к бэкенду не уходят.

Таблица 34 — Цели прокси dev-сервера

| Переменная | Локальный `backend/compose.yaml` | Стенд за nginx |
|---|---|---|
| `VITE_CARD_API_PROXY_TARGET` | `http://127.0.0.1:8080` | `https://<домен>/student-api` |
| `VITE_AUTH_API_PROXY_TARGET` | `http://127.0.0.1:8084` | `https://<домен>/auth-api` |
| `VITE_ADMIN_API_PROXY_TARGET` | `http://127.0.0.1:8082` | `https://<домен>/admin-api` |
| `VITE_REALTIME_GATEWAY_PROXY_TARGET` | `http://127.0.0.1:8081` | `https://<домен>/realtime-gateway` |

Корневой Compose порты сервисов наружу не публикует, поэтому к полному стенду dev-сервер подключается только через nginx.

**Демо-режим.** `VITE_DEMO=true npm run dev` включает все моки кабинета преподавателя. Вход демо-режим не подменяет: нужен работающий auth-api.

**Сборка статики:**

```shell
cd frontend
npm ci
npm run build               # tsc -b и vite build → frontend/dist
```

`dist/` раздаёт любой веб-сервер с fallback на `index.html` и проксированием `/student-api`, `/auth-api`, `/realtime-gateway`, `/admin-api`. Готовая конфигурация — `frontend/Dockerfile` и `frontend/nginx/`.

## 6.6. Восстановление после сбоя

- Долгоживущие сервисы перезапускаются автоматически (`restart: unless-stopped`). Одноразовые сервисы безопасно запускать повторно: `migrate` применяет только недостающие миграции, `kafka-init` создаёт топики с `--if-not-exists`.
- Состояние хранится в именованных томах: PostgreSQL (primary и replica), Kafka, SeaweedFS, Prometheus, Loki, Grafana, сертификаты. Резервное копирование томов и дамп PostgreSQL настраиваются при развёртывании.
- Потерянные при сбое события браузер добирает запросом к REST после восстановления SSE-соединения.
- Попытка, у которой АРМ не подтверждал присутствие 30 с, прерывается сервером и оценивается по сделанному. Обучаемому назначают новую попытку.

## 6.7. Сценарий ручной проверки

1. Открыть стенд и войти преподавателем `yWJJ9_z`. Откроется «Обзор» кабинета преподавателя.
2. «Сценарии» → «Шаблоны» → «Сгенерировать шаблоны с ИИ», выбрать службу 103. Через 10–15 с на экране ожидания появится «Черновики готовы».
3. Открыть черновик, подтвердить или исправить каждую секцию, опубликовать.
4. Открыть сценарий «Оператор 112: два последовательных входящих звонка», назначить его обучаемому `yWJJ9_y` на позицию оператора 112. Назначить сценарий «ДДС-102: пять простых карточек» обучаемому `yWJJ9_x` на позицию диспетчера ДДС службы 102.
5. Во втором браузере войти `yWJJ9_y`, начать занятие, «Принять» вызов, разрешить микрофон, говорить с заявителем. После реплики появляется «Собеседник отвечает…», затем звучит ответ.
6. Заполнить карточку: заявитель, адрес, тип по классификатору; проверить, что список служб сформировался. Навести курсор на неактивную кнопку сохранения — подсказка покажет недостающие поля. Сохранить карточку и завершить звонок.
7. В третьем браузере войти `yWJJ9_x`, начать занятие ДДС. Раскрыть карточку в пределах 30 с, выбрать «Принята», затем «Начало реагирования» с номером наряда и комментарием.
8. У преподавателя открыть монитор занятия: таймеры против нормативов, тревоги по просрочкам, режим проектора.
9. Завершить попытки. У преподавателя открыть «На проверке» → разбор: критерии, расхождения, подсветка ошибки в адресе, запись и расшифровка звонка. Подтвердить или исправить оценку с причиной.
10. «Аналитика»: сводные плитки, тепловая карта, успеваемость, прогноз и «прогноз ↔ факт». Скачать PDF и CSV. Войти обучаемым и открыть «Мои результаты».
