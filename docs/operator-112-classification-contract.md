# Классификация карточки оператора 112

Контракт frontend и backend. Миграция и сквозной сценарий требуют проверки в рабочем окружении.

При `POST /api/v1/cards` карточка оператора передаёт `classification` вместо `event_type_id` и `features`. Объект содержит `record_id` (номер записи утверждённого JSON-классификатора), `group_code`, `feature_1_code`, `feature_2_code`, `feature_3_code`, `final_incident_type`, `routing_flags` и `excluded_service_codes`. Фронтенд получает номер, коды и итоговый тип из записи, определённой через `resolveClassification`; признак «Пострадавшие» не переводится в `victims_count`.

`PATCH /api/v1/cards/{id}` принимает обновлённый `classification` вместе с основными полями карточки. `POST`, `PATCH`, `GET /api/v1/workspaces/{workspace_id}/cards/{id}` и список `GET /api/v1/workspaces/{workspace_id}/cards` возвращают тот же объект. Это позволяет восстановить группу, признаки и итоговый тип при повторном открытии. После изменения классификации фронтенд добавляет недостающие службы, рассчитанные по записи классификатора и `routing_flags`.

При создании любой новой карточки или шаблона требуется `classification`; запросы с `event_type_id` и `features` на создание отклоняются. Старые шаблоны, сценарии и карточки пользователь актуализирует отдельно. Миграция `0021` добавляет поле `classification` в карточку и проекцию списка и разрешает `null` для старого ID в хранимых записях.

В эталоне `expected_result.card` используется `classification` той же структуры; старые `event_type_id` и `features` в эталоне недопустимы. Автоматическая оценка сравнивает поля `classification` сохранённой карточки с эталоном напрямую. Завершение процедурного задания и сведения о сценарии преподавателю используют тот же объект `classification`; для отбора процедурных шаблонов предусмотрен фильтр `classification_group_codes`.

Необязательные `applicant_full_name`, `automatic_phone_number`, `provided_phone_number` и `location_phone_number` передаются при создании и изменении карточки и возвращаются при чтении. Миграция `0022` добавляет три телефонных поля. Текст звонка остаётся в шаблоне как `initial_call.initial_utterance` для модели заявителя; расшифровки разговора хранятся отдельно от карточки.

Сервер проверяет структуру и типы объекта; соответствие `record_id` и кодов утверждённому JSON проверяет клиент.
